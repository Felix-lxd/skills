# 修复计划多轮循环校验 (plan-validation-loop)

下面是该 Skill 的完整规范。该 Skill 仅负责校验和优化修复计划，不会执行任何修复步骤或修改代码；禁止执行类行为被列为严格规则。

## 核心原则

1. **循环校验**：每轮依次通过 Phase 1~8 门禁链，发现问题 → 就地修正计划 → 重跑，直到零报错、零异常、推演无新问题引入。
2. **只出计划，不执行**：每轮产出是「更完善的计划」而非「已修复的代码」；校验通过 ≠ 修复完成，是否执行、何时执行由用户决定。
3. **单一真相源**：全程锁定一个计划文件，所有修正就地 `SearchReplace` 更新该文件。
4. **功能完成性优先**：校验的核心目标是确认计划执行后能真正解决问题、实现预期功能；原始需求与衍生需求双基准均需覆盖，缺一不可。

## ⛔ 执行边界（最高优先级，每个 Phase 入口自检）

**允许的操作（白名单）**：
- `Read` / `Glob` / `Grep` / `SearchCodebase` / `SearchMemory`：读取计划与源码、检索经验，验证计划准确性
- `SearchReplace`：**仅修改计划文件本身**
- 调用 14方审查 Skill（仅审查模式，禁止修复模式）

**禁止的操作（任一发生 → 立即终止全流程，回滚非计划文件修改，输出「⛔ 检测到执行行为，已强制终止。本技能仅校验计划，不执行计划。」）**：
- 修改/创建/删除计划文件以外的任何文件（代码、配置、数据）
- 执行 `Bash` 修改代码/数据、修改数据库、调用外部接口
- 调用执行类 Skill（`/executing-plans`���`/subagent-driven-development` 等）
- 将计划状态标为 `已执行`/`执行中`（状态最多流转到 `已通过`，`已执行` 只能由用户或执行类 Skill 标记）

## 问题处理通则（适用所有 Phase）

任一 Phase 发现问题时：
1. **报告+修正**：在本轮校验报告列出「问题+原因+措施」，用 `SearchReplace` 就地修正计划文件，禁止静默或留待执行后处理。
2. **重跑**：本轮 ❌；若新增/删除 Fix 项则回 Phase 1 重跑完整门禁链。
3. **收敛**：重复直到某轮全链通过。

## Phase 0: 计划检测与锁定

按优先级确定校验对象：

1. **用户显式指定计划文件** → 直接锁定。
2. **会话上下文或 `.qoder/plans/` 中已有计划** → 判定问题域是否匹配：
   - **同一问题域**（Fix 项指向相同文件/代码位置/功能缺陷，如同一轮 review 的迭代校验）→ 锁定该文件，后续就地修正。
   - **不同问题域**（不同执行批次/功能模块/审查来源）→ 视为无对应计划。判断依据是问题域与审查来源，不是文件是否存在；不同审查批次必须独立建计划。
3. **无对应计划** → 调用 `/writing-plans`，以 review 发现的全部问题为输入，创建含任务分解、修复步��、涉及文件、预期结果的新计划（存于 `.qoder/plans/`，文件名含审查来源时间戳）。

> ⛔ 已有同问题域计划时，禁止用 `CreatePlan` 或 `/writing-plans` 重建——会产生平行计划，破坏单一真相源。

**计划格式要求**：
- Fix 项：任务编号、问题描述、修复文件路径、修复步骤、预期结果、操作人信息、需求溯源标注、依赖关系（如有）
- 文件头部：创建时间、关联 review 轮次、状态（草稿/校验中/已通过）、需求基准（Phase 1 首轮固化，含原始需求 + 衍生需求）

## Phase 1: 需求符合性校验（需求对齐门禁）

确保计划始终锚定原始需求与衍生需求，防止多轮修正中偏离用户真实意图或遗漏衍生功能要求。

**基准确定**（按优先级，首轮以清单固化到计划头部「需求基准」章节，后续各轮以此为唯一对照，禁止靠回忆重新解读）：

### 1A. 原始需求基准
1. 用户发起本次修复的原始需求描述（原始指令、需求文档、PRD）
2. 触发本次校验的 review 报告问题清单及验收标准
3. 计划头部记录的需求背景/预期结果

### 1B. 衍生需求基准
1. `reqs/derived/` 目录下与本次修复相关的衍生需求文��（如状态机、断电恢复、操作日志、权限、回调等）
2. 衍生需求索引 `reqs/derived/衍生需求索引.md` 中关联的功能条目
3. 衍生需求中定义的接口契约、状态流转、数据结构等约束

> **检索规则**：根据 Fix 项涉及的功能域，自动检索 `reqs/derived/` 中相关文档；若 Fix 项涉及跨域改动，需检索所有可能受影响的衍生需求。无关联衍生需求时，在计划中显式标注「本项无关联衍生需求」。

**逐条对照双基准校验**：

| 维度 | 检查内容 | 不满足时的解决措施 |
|------|---------|------------------|
| 原始需求-遗漏 | 每项原始需求都有对应 Fix 项覆盖 | 补充缺失的 Fix 项 |
| 原始需求-偏离 | 修复方向/预期结果符合原始需求意图（而非仅满足字面） | 修正 Fix 项的修复步骤与预期结果 |
| 衍生需求-遗漏 | 涉及的衍生需求条目均有对应 Fix 项或已在既有 Fix 项中覆盖 | 补充缺失的 Fix 项，标注溯源到具体衍生需求条目 |
| 衍生需求-偏离 | 修复后的行为符合衍生需求定义（状态流转、接口契约、数据结构等） | 修正 Fix 项使其满足衍生需求约束 |
| 超范围 | 无需求外改动（未要求的重构/优化/顺手修改） | 移除或降级为建议项，并标注理由 |
| 验收可对齐 | 每个 Fix 项可溯源到具体原始需求或衍生需求条目 | 补充需求溯源标注（标注来源：原始/衍生 + 文档编号）|

需求本身有歧义且无法从基准材料裁决时，记录到计划「待用户确认」章节，由用户裁决，不得臆断。

## Phase 7: 功能完成性验证与执行效果推演

推演「如果执行该计划」的后果，**首要验证计划执行后是否真正解决问题并实现预期功能**。纯静态推演（基于 Read/Grep 的影响分析），不执行任何修复步骤，完全受执行边界管辖。

### 7.1 问题解决性
逐条对照原始问题清单，推演 Fix 项执行后每个原问题是否将被解决；任一未解决 → ❌，补充修复项并入计划。

### 7.2 功能实现完整性（双基准验证）
对照 Phase 1 固化的需求基准（原始需求 + 衍生需求），逐条验证：

| 验证维度 | 验证方法 | 不通过判定 |
|---------|---------|----------|
| 原始需求功能点 | 每个原始需求功能点是否有 Fix 项实现，推演实现后的行为是否匹配需求预期 | 功能点未实现或行为不匹配 → ❌ |
| 衍生需求功能点 | 每个涉及的衍生需求功能点是否被满足（状态流转正确、接口契约一致、数据结构合规） | 衍生约束未满足 → ❌ |
| 验收标准可达 | 需求中定义的验收条件，推演执行后是否全部可达 | 任一验收条件不可达 → ❌ |
| 功能一致性 | Fix 项组合后的整体功能是否与需求描述的完整功能一致（非仅局部正确） | 局部正确但整体功能缺失 → ❌ |

> **核心问题**：计划执行完毕后，用户所期望的功能是否完整可用？是否满足原始需求和衍生需求定义的全部功能点？如果答案不是明确的「是」，则判定 ❌ 并补充/修正 Fix 项。

### 7.3 新问题引入
推演执行后是否引入新问题，至少覆盖：
   - 修改点上下游调用方因签名/行为/数据结构变化而破坏
   - 回归（破坏既有已通过的功能/测试）
   - Fix 项之间执行顺序冲突或相互覆盖
   - 同构位置遗漏（同名文件、复制代码、跨模块引用）导致执行后不一致
   - 配置/数据库/接口契约等跨系统连锁影响

任一不通过 → 按问题处理通则并入计划重跑，直到推演确认：原问题全部解决、预期功能全部实现、且不再引入任何新问题。

## 轮次策略（基于9轮实战）

- 每轮标注「第N轮」，引用上轮问题及修复状态，聚焦增量内容（不重复验证已通过项）
- 连续3轮无新问题时可合并校验维度加速收敛
- 常见收敛路径：第1-3轮扩展修复范围（同名文件遗漏）→ 第4-5轮文档内跨章节一致性 → 第6轮通过；后续轮次的 Fix 项冲突复核多为误报，需深入分析后再定论

## 红旗清单（出现任一念头 → 立即停止）

| 念头 | 现实 |
|------|------|
| "顺手把代码也改了" | 只能修改计划文件，其余一律回滚 |
| "新问题不大，执行时再处理" | 必须并入计划并重跑完整门禁链 |
| "需求我记得，不用再看基准" | 只对照计划头部固化的需求基准（原始+衍生） |
